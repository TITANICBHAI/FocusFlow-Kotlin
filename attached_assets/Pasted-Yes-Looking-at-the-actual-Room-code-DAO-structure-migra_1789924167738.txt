Yes. Looking at the actual Room code, DAO structure, migrations, and repositories, I would **keep Room** and harden the database layer rather than replace it. The current Room model is already sound in several places; the missing pieces are mostly around **migration safety, invariants, schema discipline, testing, query performance, and separating legacy-compatibility code from the normal database path**.

Android’s current architecture guidance recommends repositories as the boundary around data sources, a single source of truth, immutable data out of the data layer, and coroutine/Flow-based access; your current repository/DAO structure is aligned with that direction. ([Android Developers][1])

## What is already good

Your current Room layer already gets several important things right:

```text
Room
 ├─ entities
 ├─ typed DAOs
 ├─ suspend writes
 ├─ Flow reads
 ├─ repository mapping
 ├─ explicit indices
 ├─ versioned migrations
 └─ exported schema
```

Using `suspend` for one-shot reads/writes and `Flow` for observable queries is exactly the intended Room model. ([Android Developers][2])

The task repository also correctly keeps the database model separate from the domain model and preserves the three-state semantics of `focusAllowedPackages`. That is worth keeping.

# What I would change

## 1. Fix migration testing before adding more schema

This is the biggest gap.

You have:

```kotlin

```

and a real migration chain:

```text

```

but the uploaded project contains **no Room migration tests**.

Android explicitly recommends testing migrations and keeping exported schemas under version control. ([Android Developers][3])

And because your app has a particularly unusual legacy situation — an RN database with `user_version = 0` plus a Kotlin bootstrap shim — this isn't optional.

The agent should create migration tests for:

```text

old RN database, schema with focus_allowed_packages
RN database with settings
RN database with report_notes
RN database with existing tasks/sessions
RN database with legacy achievements/weekly insights if present
```

Most importantly, test the **actual old SQLite file**, not just synthetic tables generated by the new Room schema.

## 2. Separate "legacy RN migration" from normal Room migrations

This is currently the least clean part of `FocusFlowDatabase.kt`.

`prepareLegacyDatabase()` directly opens:

```kotlin
SQLiteDatabase.openDatabase(...)
```

and mutates `user_version` before Room starts.

That is understandable for compatibility, but it shouldn't become part of your normal database architecture.

I would organize it as:

```text
data/local/
    FocusFlowDatabase.kt
    LegacyDatabaseImporter.kt
    migration/
        RoomMigrations.kt
        LegacySchemaInspector.kt
```

Then:

```text
App startup
    ↓
LegacyDatabaseImporter
    ↓
ensure old RN DB can be consumed
    ↓
Room.databaseBuilder(...)
```

The Room database itself should stay declarative and boring.

This makes it much safer when version 5, 6, 7... arrive later.

# 3. The report-notes migration is currently a real bug

This should be fixed before production.

The migration queries:

```sql
WHERE type = 'daily'
```

but the RN schema uses:

```text
day
week
```

So the migration doesn't fully reproduce the RN data model.

And it only migrates the day notes, not the week notes.

I would **not continue the SharedPreferences design for report notes**.

The clean model is:

```text
Room
└── report_notes
      PK = (ref_date, type)
```

because it is:

* date-oriented
* queryable
* historical
* potentially multiple rows
* already represented as a relational table in RN

SharedPreferences is a poor fit for that.

# 4. Keep settings out of Room, but move ordinary settings toward DataStore later

This is the important distinction:

### Domain/relational data

```text
Room
    tasks
    focus_sessions
    focus_overrides
    daily_completions
    report_notes
    achievements
    weekly_insights
```

### Ordinary user preferences

```text
Preferences DataStore

```

### Native enforcement snapshot

```text
SharedPreferences

    active task snapshot
    standalone enforcement
    VPN/native blocking state

```

Android specifically identifies DataStore as the right fit for small key-value preferences, while repositories should hide the underlying source from the rest of the app. ([Android Developers][1])

I would **not migrate this all at once**. Preserve the native enforcement contract first.

# 5. Add real database invariants, but don't blindly add foreign keys

This needs some judgment.

You have:

```text
focus_sessions.task_id
focus_overrides.task_id
```

but tasks can be deleted.

Your existing analytics deliberately tolerate sessions whose task has disappeared, using a `LEFT JOIN`.

That means blindly adding:

```sql
FOREIGN KEY(task_id) REFERENCES tasks(id)
ON DELETE CASCADE
```

would be wrong because you'd lose historical sessions when deleting a task.

So for this particular product:

```text
DO NOT add CASCADE foreign keys just because "foreign keys are best practice."
```

Instead, document the intentional invariant:

```text
task deletion does not delete historical focus sessions/overrides
```

and test it.

Android supports foreign keys and recommends proper child indexes when using them, but the application's desired deletion semantics have to come first. ([Android Developers][4])

---

# 6. Enforce "one active focus session" explicitly

This is more important.

Currently:

```sql
SELECT *
FROM focus_sessions
WHERE is_active = 1
ORDER BY id DESC
LIMIT 1
```

is defensive because the DB **allows multiple active rows**.

That means the application invariant is:

```text
there should be exactly 0 or 1 active sessions
```

but the schema doesn't enforce it.

I'd make that invariant explicit.

Because a normal Room `@Index` cannot express the partial uniqueness you want, this is a manual migration concern.

Target:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS
idx_focus_sessions_one_active
ON focus_sessions(is_active)
WHERE is_active = 1;
```

But **do not add that migration blindly**.

Before introducing it:

```text
1. query all active sessions
2. choose the authoritative one
3. deactivate/delete invalid duplicates
4. then create the unique partial index
```

That turns a defensive convention into a database-enforced invariant.

---

# 7. Add the missing index for active-session lookup

Your current index is:

```text
(task_id, is_active)
```

but your most important query is:

```sql
WHERE is_active = 1
ORDER BY id DESC
LIMIT 1
```

The existing composite index is not ideal for that access pattern because `task_id` comes first.

So I'd add a dedicated index for the actual query, after measuring/query-plan validation:

```sql
CREATE INDEX idx_focus_sessions_active
ON focus_sessions(is_active, id DESC);
```

You don't need to add indexes everywhere. Only where the actual read patterns justify them.

# 8. Review every JSON-in-SQL column individually

You currently have:

```text
tasks.tags
tasks.reminders
tasks.focus_allowed_packages

focus_sessions.allowed_packages
```

This isn't automatically bad.

### Keep JSON when:

```text
the app reads/writes the collection as a whole
and
you don't need SQL filtering/joins on its elements
```

That currently fits `focus_allowed_packages` and probably `allowed_packages`.

### Consider normalization when:

```text
you need queries like:
    "find all tasks with tag X"
    "show every task containing package Y"
    "find reminders due between A and B"
```

Then a proper child table becomes better.

So don't normalize just for theoretical purity.

# 9. Fix the DAO query/result-type boundaries

The DAOs are generally good, but I would enforce a clean distinction:

```text
DAO
    SQL + database-shaped DTOs

Repository
    domain mapping + business-oriented operations

Domain
    Task / FocusSession / analytics models

UI
    never sees DAO projections
```

You're mostly doing this already.

For example:

```kotlin

```

are database projections, which is good.

Don't start leaking these directly into Compose/ViewModels.

Android's repository guidance specifically recommends keeping data-source details behind repositories. ([Android Developers][1])

# 10. Use explicit transaction boundaries for multi-step domain operations

`@Update(List)` is fine for the batch update you're doing.

Room supports transactional DAO operations and queues transactions so only one runs at a time. ([Android Developers][5])

But some of your **domain operations** involve multiple tables:

```text
complete focus session
    ↓
end session
    ↓
update task
    ↓
daily completion
    ↓
analytics/achievement side effects
```

Those shouldn't accidentally become:

```text
UPDATE A
commit

UPDATE B
commit

UPDATE C
crash
```

Where the product semantics require atomicity, put the whole DB portion inside:

```kotlin
db.withTransaction {
    ...
}
```

or a DAO transaction method.

Android explicitly provides `RoomDatabase.withTransaction` for this purpose. ([Android Developers][5])

Important distinction:

```text
DB transaction:
    task/session/completion database invariants

NOT transaction:
    notification
    alarm
    service start
    widget refresh
    external Android side effect
```

Those external effects should happen after the database commit, with retry/reconciliation where necessary.

# 11. Add a database-operation policy

Your agent should establish this explicitly:

```text
READ
    DAO suspend / Flow

WRITE
    DAO suspend

MULTI-TABLE WRITE
    Room withTransaction

DOMAIN ACCESS
    Repository only

UI
    Repository/ViewModel only

RAW SQLite
    Migration/legacy-import layer only
```

The last one is particularly important.

Currently raw SQLite appears in `FocusFlowDatabase.kt` for migration/import. That's fine.

It should **not spread elsewhere**.

# 12. Database writes should remain main-safe

Room's coroutine integration is designed around `suspend` DAO operations, and Android recommends repository/data-source APIs that are safe to call from the main thread. ([Android Developers][2])

That means the repositories should not require every caller to remember:

```kotlin
withContext(Dispatchers.IO)
```

around each database call.

Instead, the data layer should expose main-safe suspend APIs and let Room handle its database executor.

So I'd avoid scattering manual `Dispatchers.IO` all over the application.

---

# 13. Migration strategy: use AutoMigration where it actually helps

Your legacy RN transition absolutely requires manual migrations.

But future trivial Room-only changes don't necessarily need hand-written SQL.

Android recommends Room `AutoMigration` for straightforward schema changes and manual migrations when the change is ambiguous or requires custom data transformation. ([Android Developers][3])

So after the RN compatibility migration chain is finished:

```text
legacy RN → Kotlin
    manual

future simple Room-only changes
    AutoMigration

renames / data transformations / semantic changes
    manual Migration + spec
```

That keeps the migration code smaller over time.

# 16. Add destructive-migration policy explicitly

I would **not** add:

```kotlin
.fallbackToDestructiveMigration()
```

to this database.

For a productivity app with task history, focus sessions, reports, achievements, and user configuration, silently deleting the DB is too dangerous.

Instead:

```text
supported migration
    ↓
success

unsupported/corrupt migration
    ↓
diagnostic
    ↓
recovery/import path
    ↓
never silently wipe user data
```

This is especially important because you're converting an existing RN database in-place.

# 17. Database corruption/recovery needs its own policy

RN has a fairly elaborate:

```text
health probe
retry
dead-handle reset
WAL checkpoint
diagnostic logging
```

You don't need to clone all of it into Kotlin.

Room is already giving you a more robust database abstraction.

But you should still define what happens if:

```text
database open fails
migration fails
SQLiteException occurs
database file is corrupt
disk is full
WAL cannot be opened
```

The application should not turn every database exception into:

```text
blank UI
```

or destructive reset.

It should surface a recoverable application state and record the event through the startup diagnostics system.

## The priority order I would use

This matters because I **wouldn't have the agent do all of that simultaneously**.

```text
P0 — before anything else
    Fix report_notes migration
    Add migration fixtures/tests
    Verify actual RN database opening
    Verify schema export

P1
    Make report_notes Room-backed
    Add active-session invariant
    Add/verify transaction boundaries
    Audit query plans/indexes

P2

    Harden corruption/recovery
    Document JSON-vs-relational decisions

P3
```

The key architectural distinction is that **Room should own durable relational history, DataStore should eventually own ordinary user preferences, and SharedPreferences should remain only where native Android components need a small immediately-readable enforcement snapshot**. And the most urgent concrete defect from the current code is still the `report_notes` migration mismatch. I would fix and test that before making any broader persistence migration.
