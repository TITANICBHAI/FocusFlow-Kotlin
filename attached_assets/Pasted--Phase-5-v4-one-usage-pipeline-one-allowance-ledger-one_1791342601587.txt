## 1. What changed in v4

1. **Minimum-version mismatch resolved (section 2).** The owner's range is Android 10 to latest. The code still carries **51 version checks in 19 files that were written for older minimums** (below API 29), and the upload contains no Gradle or `uses-sdk` entry, so the real `minSdk` is unverified.

## 3. Compatibility contract (Android 10 to latest)

### 3.1 Rules

1. **Event types** the pipeline needs exist natively on API 29: `ACTIVITY_RESUMED/PAUSED/STOPPED` and `DEVICE_STARTUP/SHUTDOWN` (API 29); `SCREEN_INTERACTIVE/NON_INTERACTIVE` and `KEYGUARD_SHOWN/HIDDEN` (API 28) (docs).
2. **The pipeline is pure.** API-level handling lives only in the thin adapter over `UsageStatsRepository`.
3. **The adapter must handle:**
   - `queryEvents` returning **null** before the first unlock after boot (Android 11+, docs). Treat as "unknown", never as zero usage. Our current code does not handle this.
   - `SecurityException` when usage access is revoked.
   - The system keeping events **only for a few days** (docs). Never assume older data exists.
4. **Do not use `UsageEventsQuery`** (API 35+, docs) without a version check. It is optional.
5. **Usage-access check:** use `unsafeCheckOpNoThrow` (API 29+). Our code uses the deprecated `checkOpNoThrow`.
6. **Day boundaries:** calendar arithmetic (DST days are 23 or 25 hours).
7. **Binder calls off the main thread.** Enforcement reads in-memory state.
8. **CI gate:** Android Lint `NewApi` must pass in CI. Nudge documents a crash on older versions that no JVM test and no single device caught; lint did.

| # | Decision | Status |
|---|---|---|
| D1 | Allowance counts usage **all day**, not only during blocks. | Decided |

Open items (defaults apply if not answered):

- **O1. Interval-mode window start.** Default: starts at the first open of the app regardless of block state.
- **O2. What counts as an "open".** Default: every new foreground span of the package after another real app or the home screen. A short bridge only for a small allow-list of system dialog packages (permission controller, the system chooser): A → dialog → A within a few seconds is one open. No generic debounce.
- **O3. Replace the 60 s polling sync** with a tick that runs only while an allowance app is in the foreground (default 30 s, like Nudge) plus recompute on app open, service start and day rollover.
- **O4. Allowance when usage data is unavailable for a long time** (section 7.5). Default: **keep estimating, do not lock the user out**.
- **O5. Launch count shown on Stats and used by streak detection.** Default: the pipeline's span starts (same rule as O2). Today's Stats card uses a 30 s debounce, so displayed launch counts will change. Say so in release notes.
- **O6. Detector continuity across the source seam** (section 8.4). Default: **strict**, one source per evaluated window. Relax later only if the shadow-period comparison shows the sources agree within a tolerance the owner sets.

## 5. The pipeline rules (from Nudge and Device-Watch, confirmed by the docs)

Implement as one pure, JVM-testable class (suggested name `ForegroundSpanTracker`), fed events in time order and emitting non-overlapping `[start, end)` spans per package:

1. **One foreground package at a time.** A `RESUMED` for a different package closes the open span at that instant.
2. **Everything that ends the foreground ends the span:** `PAUSED`; `STOPPED` as a backstop; `SCREEN_NON_INTERACTIVE`; `KEYGUARD_SHOWN`; `DEVICE_SHUTDOWN` (docs: treat shutdown as all activities stopped; no explicit `STOPPED` events are generated).
3. **Match `STOPPED` to the activity.** Moving inside an app emits `A paused, B resumed, A stopped`; a package-wide stop would close B's new span. Nudge matches the exact activity class; Device-Watch keeps a set of open classes per package. Start with the simpler; choose in 5.0.
4. **Cap the inferred tail.** An open span only has an observed start. Extended to "now" it is capped (Nudge: 4 h). Measured spans are never capped.
5. **Filter spans, never the stream.** Feed every event (including our own package and launchers); drop packages afterwards.
6. **One query pass over the window**; spans split at day boundaries.
7. **One place interprets platform event types.** Weekly bars, hourly bars, launches, sessions and allowance all read the same pipeline. (Nudge fixed disagreeing numbers, a day showing "17 hours before lunchtime", by collapsing four copies of the pairing loop.)
8. **Opens/launches** = a package's span starts after being closed (O2). Look back before the window start so an app already open at the start is counted from the start only (we already clip this way).
9. **Launchers and our own package** are excluded from totals and rankings at span level.
10. **Null or `SecurityException` means "unknown", not zero.** Keep the last known value.

## 6. Room rollups: no duplicates, history preserved

### 6.1 What exists (code)

- `daily_app_usage`: primary key `(date, package_name)`. The live writer does read-modify-write accumulation (`addForegroundTime`, `incrementLaunchCount`); the generic `upsert` is **REPLACE**.
- `app_sessions`: auto-generated id, **no unique key**; inserts use IGNORE, which never fires because the id is generated. Inserting derived sessions would **duplicate** existing ones.
- Retention: both tables are pruned with `deleteOlderThan` (90 days).
- Database version is **6**, `exportSchema = true`, with explicit migrations 0→1 through 5→6 and no destructive fallback found in the code. The database descends from an older hybrid app that left `user_version = 0`, handled by `prepareLegacyDatabase`.

### 6.2 New tables (additive migration 6 → 7)

| Table | Key | Purpose |
|---|---|---|
| `usage_rollup_day` | `(date)` | One row per day: status `PARTIAL` or `COMPLETE`, coverage start/end (ms), `pipeline_version`, `computed_at`, total foreground ms (sanity check) |
| `usage_rollup_app_day` | `(date, package_name)` | Same shape as the legacy row so detectors can reuse it: app name, category, foreground ms, hourly ms (same 24-value format), launch count, session count, first start, last used |
| `usage_rollup_session` | `(package_name, started_at)` | One row per span; end, duration, local date. Needed by the session-based detectors |

- The existing tables are **not altered**. The migration only creates tables and indexes.
- Add the migration test with Room's migration test helper: build a version-6 database containing rows in `daily_app_usage` and `app_sessions` (and the legacy `user_version = 0` path), migrate, and assert every old row is unchanged. Commit the exported schema JSON for version 7.
- **(verify)** whether backup/export includes the Room usage tables. If it does, the new tables must be included too (rollups for old days cannot be recomputed). If it does not, document that.

### 6.3 Idempotent writes

- One writer, one mutex, **one transaction per date**: delete that date's rows in the three new tables, insert the recomputed rows. Running it twice with the same events gives the same rows.
- A `COMPLETE` day is **never downgraded**. If events for that day have aged out, skip it. A `pipeline_version` bump may recompute a day only if its events still exist.
- **Day complete** = the day is over and the earliest available event is at or before the start of that day (the 5.0 retention measurement defines the probe). The oldest available day is normally `PARTIAL`.
- Today is never stored as `COMPLETE`; it is computed live and cached as `PARTIAL`.
- Triggers: app open, service start, day rollover, and Stats open. Work per run is bounded by the few days the OS keeps.
- App name and category use the same helpers as the current tracker (`resolveAppName`, `resolveCategory`) so rows stay comparable.

### 6.4 Merged read model (one source per date)

Add one repository (suggested `UsageHistoryRepository`) that returns the **same row types the detectors and Stats already use**:

- For each date: use the rollup if its day row is `COMPLETE` at the current `pipeline_version`; otherwise use the legacy rows for that date if any exist; otherwise a `PARTIAL` rollup, marked partial.
- **Never sum two sources for the same date.** This is what prevents double counting, together with the primary keys and the single writer.
- It also returns `sourceByDate` and the **seam date** (the first date served from rollups), for section 8.4 and for the coverage notice.
- Methods mirror the existing DAO reads: daily usage range, session stats by day, first session each day, raw sessions per package.

### 6.5 Legacy writer lifecycle

- **Shadow period (5.3):** the old accessibility-fed writer keeps writing the legacy tables unchanged; the new writer writes only the new tables. No cross-writes. Both sources exist for the same days, which allows the comparison.
- **Cutover (5.5):** stop the old writer's Room writes. Keep reading legacy rows through the read model. Keep the 90-day prune for both table sets.
- **Rollback:** switching the read model back to legacy-only is a one-line change, because nothing legacy was modified.

## 7. Allowance when usage data is stale or unavailable

### 7.1 Inputs

- **Last confirmed reading:** the value and the time of the last successful pipeline read for the package (kept in the ledger).
- **Live signal:** accessibility knows which package is in the foreground and when that session started.
- The only new stored field is `confirmedAtMs` in the existing allowance JSON (additive; older readers ignore it). No new prefs keys.

### 7.2 States

| State | Meaning | Default thresholds |
|---|---|---|
| **FRESH** | Last successful read is recent | Within 2 ticks (about 60 s) while an allowance app is in the foreground |
| **STALE** | Reads are late or failing transiently (exception, timeout, null before the first unlock, slow query) | Older than the FRESH window, usage permission still granted |
| **UNAVAILABLE** | Usage access revoked, or no successful read since boot for longer than a grace period after unlock | Permission denied, or no read for 5 minutes after unlock (tune in 5.0) |

### 7.3 Estimate (used in STALE and UNAVAILABLE)

- **Time budget:** `estimated used = last confirmed value + live time since max(last confirmed time, current foreground session start)`, counted only while accessibility reports the allowance app in the foreground. Never negative; never above the day length.
- **Count:** `last confirmed count + number of new foreground session starts` seen by accessibility since the last confirmation (same O2 rule).
- **Interval:** the persisted window start decides expiry by wall clock; used time follows the time-budget estimate inside the window.
- **Day rollover:** the day key comes from the clock. A new day starts at zero and takes a baseline at the first successful read.

### 7.4 Reconcile when data returns

- The pipeline value **replaces** the estimate. Estimates are never added to it.
- The value never goes below the last **confirmed** value for that day (usage cannot decrease).
- If the estimate had already blocked an app and the pipeline value is lower, the app unblocks. Log the difference. Accept it: estimates are only a bridge.
- The exact-expiry timer is re-seeded from the new baseline.

### 7.5 Enforcement behavior

| Situation | Behavior |
|---|---|
| FRESH | Normal enforcement from the pipeline value |
| STALE | Keep enforcing using the estimate. Retry reads with backoff. Do not fail open and do not lock out |
| UNAVAILABLE | **Default (O4): same as STALE, keep estimating.** The health card already shows "Needs attention" when usage access is missing |
| UNAVAILABLE, alternative | After a grace period treat the allowance as exhausted until data returns (fail closed), or treat it as unlimited (fail open). Not recommended: fail closed punishes the user for an OS hiccup, fail open lets revoking the permission bypass the limit |
| Accessibility also down | No live signal and no pipeline: enforcement is already limited; the health card is the only signal |
| Boot, before first unlock | State is UNAVAILABLE-transient; allowance apps cannot be opened before unlock anyway. Keep the last value and read once after unlock |
| Device clock or day change during staleness | Day key from the clock; baseline at the next successful read |

### 7.6 What the user sees and what we log

- Launcher allowance card: when not FRESH, show the value with an "about" marker (copy to confirm) instead of a precise number.
- Stats: the coverage notice (section 8.2) covers missing days; no per-minute staleness UI.
- Debug logs: state transitions and the estimate-versus-confirmed delta on reconcile. No usage content beyond package names already used.

### 7.7 Tests

Pure tests for the state reducer and estimator: transitions, null and exception inputs, permission revoke and restore, boot-before-unlock, estimate then reconcile (higher and lower), monotonic-per-day rule, midnight during STALE, interval expiry by clock.

### 8.4 Source seam rules for detectors (O6)

At cutover the rollups only hold the few recent days the OS still has, so every usage detector would otherwise average **two different definitions** of the same quantity and could invent a trend at the seam.

- The read model (6.4) tells each detector which source each date came from.
- **Default (strict):** a detector evaluates only a window whose days all come from one source. If the post-seam days are too few for its minimum, it returns "not enough consistent data yet" instead of mixing. Trend detectors (escalating capture, substitution, streak lock-in, allowance suggestion) can therefore stay silent for up to about four weeks after cutover. Distribution detectors (variable reward, infinite session, morning hijack) need raw sessions from one source across the window.
- **Optional relaxation:** use the shadow period (5.3) to compare both sources on the same days. If per-app daily totals agree within a tolerance the owner sets, allow mixing for detectors whose inputs are totals (not session shapes).
- **Fingerprints:** findings are deduplicated by an evidence fingerprint that includes sample size and a quantized metric. After cutover the same pattern may produce a new fingerprint and be shown again. Check `FindingRepository.submit` behavior in 5.0 and keep fingerprint inputs unchanged.
- Add pure tests per detector for: single-source window passes; mixed window is refused; post-seam-only window with enough days passes.
- **(verify)** when `runAll` is triggered, so detector runs and rollup runs do not race. Run detectors after the rollup pass.

## 12. Ground rules

1. **No god files.** One responsibility per new file, aim under about 250 lines, justify over 300. Pure logic separated from Android calls and JVM-tested.
2. **The big files must shrink.** Net line count of `AppBlockerAccessibilityService.kt` and `ForegroundTaskService.kt` goes down in every step that touches them. Report the numbers.
3. **Label every step** behavior-preserving or behavior-changing.
4. **No new prefs keys.** The only new stored field is `confirmedAtMs` inside the existing allowance JSON. New Room tables only as in 6.2.
5. **No new polling loops.**
6. Blocking logic, VPN, keyword blocker and the foreground-service type stay untouched. Android 15 / targetSdk 35 work stays parked.
7. Every behavior-changing step updates the user-facing copy and the release notes.

## 13. What can go wrong

- **Duplicates in Room:** prevented by new tables, primary keys, one writer, one transaction per date, and one source per date. Test it.
- **Silent history loss:** the migration must not touch existing tables; the migration test is mandatory.
- **Detector silence after cutover:** expected for up to about four weeks under the strict seam rule (O6). Tell the owner before release.
- **Findings reappearing** after fingerprint changes (8.4).
- **Locked boot:** null from `queryEvents` must never reset usage to zero.
- **Split-screen / multi-resume:** "one foreground package" credits only the last resumed app. Document it; decide from 5.0.
- **Event delivery delay:** keep the exact-expiry timer and the tick.
- **Retention:** if neither the app nor the service runs for longer than the OS keeps events, history for those days is lost. The always-on service plus the rollup at day rollover is the mitigation.
- **Time travel:** changing the device clock moves the day boundary. Check whether current behavior is intended. Out of scope.
- **Numbers users will see change:** Stats totals, launch counts and some findings change once inflated spans disappear. Say so in release notes.
