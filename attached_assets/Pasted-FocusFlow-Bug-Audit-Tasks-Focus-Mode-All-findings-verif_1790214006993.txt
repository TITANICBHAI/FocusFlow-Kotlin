FocusFlow Bug Audit — Tasks & Focus Mode
All findings verified against uploaded source. Every code reference is real.

Want out of the stuck state right now, before any fix is deployed? "Emergency Override" on the Focus screen is safe to use — traced it end to end. It calls the exact same PIN-gated stopFocusMode(hash) chain as "Stop Focus," correctly ends the Room session, and its button visibility is gated only on isFocusing (which is true in the exact stuck state), so it's on-screen right now if you need it. Confirmed separately: your standalone "Block apps while I work" toggle runs on entirely independent SharedPrefs state — stopping focus mode will not touch it, and vice versa.

Part 1 — Task-Only Bugs
T1 · extendTaskTime has no task-status guard — extends completed/skipped tasks
Severity: High File: TaskViewModel.kt

fun extendTaskTime(taskId: String, minutes: Int) {
    viewModelScope.launch {
        taskOperationMutex.withLock {
            val task = taskRepository.getAllTasks()
                .firstOrNull { it.id == taskId } ?: return@withLock
            // ← NO status check here
            val newEnd = Instant.parse(task.endTime).plusMillis(minutes * 60_000L)
            taskRepository.updateTask(task.copy(endTime = newEnd.toString(), ...))
            alarmRepository.scheduleAlarm(taskId, task.title, newEndMs)
        }
    }
}
completeTask() and skipTask() both have this guard at lines 186 and 204:

if (task.status == "completed" || task.status == "skipped") return@withLock
extendTaskTime() does not. So you can call it on a completed task, which:

Moves its endTime forward in Room
Schedules a new AlarmManager alarm for the extended end time
When that alarm fires, TaskEndAlarmReceiver posts a "Time's Up" notification for a task that was already marked done days ago
Fix: Add the same two-line guard at the top of the taskOperationMutex.withLock block.

T2 · updateTask reschedules alarms for any task regardless of status
Severity: Medium File: TaskViewModel.kt

fun updateTask(task: Task) {
    viewModelScope.launch {
        taskOperationMutex.withLock { taskRepository.updateTask(task) }
        alarmRepository.cancelAlarm(task.id)
        val endMs = Instant.parse(task.endTime).toEpochMilli()
        if (endMs > System.currentTimeMillis()) {
            alarmRepository.scheduleAlarm(task.id, task.title, endMs)  // no status check
        }
    }
}
If the Edit Task sheet is opened on a completed task and saved with a future end time, a real alarm is scheduled. At that end time, TaskEndAlarmReceiver fires the "Time's Up" notification for a completed task. No crash, but a confusing ghost notification.

Fix: After the mutex block, check task.status before scheduling:

if (endMs > System.currentTimeMillis() &&
    task.status !in setOf("completed", "skipped")) {
    alarmRepository.scheduleAlarm(...)
}
T3 · Alarm operations are outside the mutex in addTask and updateTask
Severity: Medium File: TaskViewModel.kt

fun addTask(task: Task) {
    viewModelScope.launch {
        taskOperationMutex.withLock { taskRepository.insertTask(task) }  // lock released
        // ↓ alarm scheduled after the lock is gone
        alarmRepository.scheduleAlarm(task.id, task.title, endMs)
    }
}
The mutex protects the Room write but not the alarm scheduling. This creates two problems:

Crash window: If the process is killed between the Room insert and scheduleAlarm(), the task exists in the DB with no alarm. There is no boot-time alarm recovery that checks for tasks with missing alarms — AppBootViewModel only recovers focus sessions, not task alarms.

Race on rapid edits: updateTask cancels and reschedules the alarm outside the mutex. Two rapid updateTask calls can interleave: call-1 cancels alarm, call-2 cancels (nothing), call-2 schedules alarm for its end time, call-1 schedules alarm for its end time. Final alarm is whichever ran last, not the one from the most recent Room write.

Fix: Move alarm operations inside taskOperationMutex.withLock in both methods.

T4 · Every single-task lookup loads the entire tasks table
Severity: Medium File: TaskViewModel.kt, TaskDao.kt

TaskDao has no getTaskById(). Every status mutation does:

val task = taskRepository.getAllTasks().firstOrNull { it.id == taskId }
// getAllTasks() = observeAllTasks().first() = full table emit
Three functions do this: completeTask, skipTask, extendTaskTime. On a schedule with 50+ tasks this loads all rows from Room on every status change.

Fix:

// TaskDao.kt
@Query("SELECT * FROM tasks WHERE id = :taskId LIMIT 1")
suspend fun getTaskById(taskId: String): TaskEntity?
Then replace getAllTasks().firstOrNull { it.id == taskId } with getTaskById(taskId) in all three callers.

T5 · addTask doesn't validate endTime > startTime
Severity: Low File: TaskViewModel.kt

A task created with endTime <= startTime inserts fine, is immediately in an "overdue" display state from birth, and gets no alarm (endMs <= currentTimeMillis → scheduleAlarm is skipped). The Schedule screen's isRunningNow() returns false (no time window active), isAwaitingDecision() returns true immediately (endTime already past), so the "Time's Up" banner appears the moment the task is created.

Fix: Validate before insert:

val start = Instant.parse(task.startTime)
val end = Instant.parse(task.endTime)
if (!end.isAfter(start)) return  // or show a UI error
T6 · SchedulerEngine is now type-correct but still 100% unwired — the Defense screen's "Auto-reschedule freed time" toggle does nothing
Severity: High (upgraded — this is a user-facing broken promise, not just dead code) File: SchedulerEngine.kt, DefenseScreen.kt, TaskViewModel.kt, AppModule.kt

The type-mismatch part of the original T6 finding is fixed. SchedulerEngine.kt now has import com.tbtechs.focusflow.data.model.Task as AppTask and typealias Task = AppTask — every function in the file (detectConflicts, findNextAvailableSlot, rebalanceAfterOverrun, insertTaskSafe, compressSchedule, compressDeletedTaskGap, getUnfinishedOverdueTasks, analyzeScheduleHealth) now genuinely operates on the real domain Task. TaskStatus/TaskPriority are objects with lowercase string constants ("completed", "skipped", "scheduled", "active", "low"/"medium"/"high"/"critical") that match the rest of the app's convention exactly — no silent string-case mismatch. This is a clean, correct, framework-free "pure Kotlin port" (its own doc comment's words) — it's good code.

But it's still never called from anywhere. Grepped the entire codebase for SchedulerEngine: it appears in exactly two files — its own definition, and one doc comment on AppModule.taskRepository ("Also consumed by [SchedulerEngine] for conflict detection") that describes an intended relationship, not an actual one. There is no SchedulerEngine(...) instantiation anywhere, not in AppModule, not in TaskViewModel, not in any background worker. TaskViewModel.kt's completeTask, skipTask, deleteTask, and clearAllTasksExcept — the exact four actions the Defense screen's toggle description names — have zero reference to SchedulerEngine or to settings.autoRescheduleEnabled.

This makes the toggle itself the concrete, user-visible bug. In DefenseScreen.kt:

SettingSwitch(
    label = "Auto-reschedule freed time",
    description = if (settings.autoRescheduleEnabled) {
        "On — completing, skipping, or deleting a future task moves later tasks forward"
    } else {
        "Off — task times stay unchanged when time is freed"
    },
    checked = settings.autoRescheduleEnabled,
    onChange = { enabled -> update(settings.copy(autoRescheduleEnabled = enabled)) },
)
Toggling this on makes an explicit behavioral promise to the user. autoRescheduleEnabled is persisted correctly (confirmed in SettingsViewModel/SettingsRepository/AppSettings) but is never read anywhere except that one persistence round-trip. Completing, skipping, or deleting a task never moves anything, regardless of what this switch is set to — it's currently a placebo control.

What each part of the promise maps to, concretely (verified against the actual function bodies):

"completing... moves later tasks forward" → compressSchedule(completedTask, completedAt, allTasks). Confirmed: if a task finishes before its planned endTime, this shifts every later scheduled task earlier by the minutes saved.
"deleting... moves later tasks forward" → compressDeletedTaskGap(deletedTask, allTasks). Confirmed: shifts every later task whose status is still TaskStatus.SCHEDULED earlier by the deleted task's duration.
"skipping... moves later tasks forward" → no dedicated function exists for this case. The only skip-adjacent logic is inside rebalanceAfterOverrun, which does the opposite (pushes later tasks back, or auto-skips medium/low-priority ones) — that function is for a task running over its time, not for a manual skip freeing time up. Whether "skip" should reuse compressDeletedTaskGap's logic (treat the skipped slot like a deleted one) is a product decision the port doesn't make for you — worth deciding explicitly rather than assuming.
Fix sketch (shape only — this needs your judgment on the "skip" gap above, not a paste-in patch):

// AppModule.kt — instantiate it like every other singleton
lateinit var schedulerEngine: SchedulerEngine
// ... schedulerEngine = SchedulerEngine()

// TaskViewModel.kt — inside completeTask, after the status write, inside the same lock:
if (settingsRepository.readAppSettings().autoRescheduleEnabled) {
    val updated = schedulerEngine.compressSchedule(task, nowIso(), taskRepository.getAllTasks())
    updated.filter { it.id != task.id }.forEach { taskRepository.updateTask(it) }
}
// deleteTask: same idea with compressDeletedTaskGap instead
Note this would need its own status-guard and mutex discipline (per T1/T3/T4 above) to avoid reintroducing those same classes of bug in the new call site.

Also worth knowing independent of the wiring gap: rebalanceAfterOverrun will auto-skip medium-or-lower-priority tasks without asking, once the cumulative shift exceeds options.maxAutoShiftMinutes. If you wire this one up too (for the overrun case, separate from the toggle above), that auto-skip behavior deserves a confirmation dialog rather than firing silently — tasks disappearing from someone's schedule without them clicking anything is a rough experience.

Part 2 — Focus Mode-Only Bugs
F1 · ACTION_TASK_ENDED is broadcast but received by nobody — Room session never ends
Severity: Critical File: ForegroundTaskService.kt lines 724, 752; searched entire codebase

When the focus timer reaches zero, tickRunnable fires:

clearFocusActive()     // writes focus_active=false to SharedPrefs
sendBroadcast(Intent(ACTION_TASK_ENDED)...)
triggerTaskAlarm(...)  // posts the "Time's Up" notification
goIdle()               // clears service in-memory state
clearFocusActive() only writes to SharedPrefs. It does not call focusSessionDao.endSession(). ACTION_TASK_ENDED is searched in every extracted file:

Defined once: ForegroundTaskService line 76
Sent twice: lines 724 and 752
Received: zero times
No component — not FocusSessionViewModel, not MainActivity, not any BroadcastReceiver — registers for this action. The consequence:

Room's focus_sessions.is_active stays 1 indefinitely
FocusSessionRepository.observeActiveFocusSession() → FocusSessionDao.observeActiveSession() keeps emitting the live session
FocusSessionViewModel.init collects it → _focusSession.value never becomes null
isFocusing = session?.isActive == true stays true forever
The Focus screen shows "Focus Mode Active" with an ever-growing overdue timer
App blocking stops (SharedPrefs cleared) but the UI says focus is active
This is the architectural root cause of the bug from the screenshots.

This gap was anticipated, not just missed. ForegroundServiceController.stopServiceInternal()'s own doc comment reads: "Authorized system transition... task completion, skipping, and orphan-session reconciliation use this path" — and it's deliberately PIN-free for exactly that reason. But grepping every call site: it has exactly one caller, inside the manual stopFocusModeAwait() path. No automatic orphan-reconciliation trigger was ever built to use it. The authorization primitive for fixing F1 already exists in the codebase — it's just never invoked automatically.

Fix: In FocusSessionViewModel.init, register a receiver:

private val taskEndedReceiver = object : BroadcastReceiver() {
    override fun onReceive(ctx: Context, intent: Intent) {
        viewModelScope.launch {
            focusSessionRepository.getActiveFocusSession()?.let { s ->
                focusSessionRepository.endFocusSession(s.taskId)
            }
            _focusSession.value = null
        }
    }
}
// in init:
ContextCompat.registerReceiver(
    context, taskEndedReceiver,
    IntentFilter(ForegroundTaskService.ACTION_TASK_ENDED),
    ContextCompat.RECEIVER_NOT_EXPORTED,
)
// in onCleared:
context.unregisterReceiver(taskEndedReceiver)

F3 · stopFocusModeAwait has no try-catch — SessionPinRequiredException kills the coroutine silently
Severity: Critical File: FocusSessionViewModel.kt

suspend fun stopFocusModeAwait(pinHash: String? = null) {
    val current = _focusSession.value
        ?: focusSessionRepository.getActiveFocusSession() ?: return

    settingsRepository.setFocusActive(active = false, pinHash = pinHash)
    // ↑ throws SessionPinRequiredException if PIN set and pinHash == null

    focusSessionRepository.endFocusSession(current.taskId)  // never reached
    settingsRepository.clearActiveTask()                     // never reached
    foregroundServiceController.stopServiceInternal()        // never reached
    _focusSession.value = null                               // never reached
}
stopFocusMode() calls this via viewModelScope.launch { stopFocusModeAwait(pinHash) }. There is no try-catch anywhere in the chain. SessionPinRequiredException propagates into the coroutine scope and is swallowed silently. The result:

Room session stays active (is_active = 1)
SharedPrefs unchanged (setFocusActive throws before writing)
Service still running
_focusSession.value still non-null
User sees no error, no feedback, nothing changes
This triggers whenever stopFocusMode(null) is called and a session PIN is configured. This call path is used by: the Done button's conditional branch, the schedule screen's ✓ button, and stopAfterConfirmation(). Only requestStop() (the "Stop Focus" button) correctly gates on PIN before calling.

fun stopFocusMode(pinHash: String? = null) {
    viewModelScope.launch {
        try {
            stopFocusModeAwait(pinHash)
        } catch (e: SessionPinRequiredException) {
            _stopRequiresPinEvent.emit(Unit)  // tell UI to show PIN dialog
        }
    }
}

AB5 · A phone reboot will NOT clear an F1-orphaned session
Severity: Informational (confirms a workaround does not work) File: BootReceiver.kt

Traced the exact screenshot scenario through BootReceiver. By the time the stuck "+3m overdue" state exists, clearFocusActive() has already run, so focus_active = false in SharedPrefs. New: Pomodoro break — fully traced, no bugs found
Since startPomodoroBreak/endPomodoroBreak are new, I traced the whole mechanism given it's squarely focus-mode territory:

Blocking correctly pauses during break. enterBreak() sets focus_active=false in the same shared prefs file the accessibility service reads — so break time is genuinely unblocked, not just cosmetically "on break."
Blocking correctly resumes. resumeFromBreak() sets focus_active=true, restarts the normal tick loop, rebuilds the active notification with the correct remaining time.
A break can't swallow the task's real end. breakTickRunnable checks endTimeMs before checking whether the break itself has expired — if the task's actual end time arrives mid-break, it fires the full ACTION_TASK_ENDED sequence instead of silently continuing the break past it. There's a comment calling this out explicitly as an intentional guard.
Stopping focus mid-break is clean. ACTION_SET_IDLE's handler cancels breakTickRunnable and calls goIdle(), which now clears focus_break_until_ms too (per the AB6 fix above).
One harmless, sub-second timing overlap: the ViewModel's own 1-second break-expiry poll and the service's independent breakTickRunnable can both notice expiry within ~1s of each other and both write the same (idempotent) prefs values. Not worth fixing — it's not visible to the user and doesn't produce inconsistent state, just slightly redundant writes.
