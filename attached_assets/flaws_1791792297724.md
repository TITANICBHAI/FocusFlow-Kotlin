# Fixes Plan and Tracker Flaws

**Audit date:** 2026-10-11
**Scope:** Dependency order, batch gates, acceptance criteria, and owner-run checks in `fixes/PLAN.md` v8 and the current `fixes/TRACKER.md`. This is a planning-document audit, not a source-code review. No proposed plan or tracker corrections are applied here.

## Summary

The plan has **three hard dependency cycles**, conditional gate risks, and acceptance, sequencing, and status inconsistencies. This does not prevent all work: the owner authorized independent B1 work to proceed, with its resolver-dependent fallback portion deferred until B6. That sequencing exception is recorded in the tracker; no app source has been changed for B1.

## Hard dependency cycles

### F-01 — A2 maintenance worker and C5 retention block each other

**Evidence**
- Plan §5 A2 requires the maintenance worker to run pruning and says it must call the rollup pruning added in C5 (`fixes/PLAN.md`, A2).
- The tracker leaves A2's rollup-pruning item blocked by C5 (`fixes/TRACKER.md`, A2).
- C5 is blocked by A1–A4, and the Batch C gate also requires A1–A4 to be done (`fixes/TRACKER.md`, C5 and Batch C gate).
- A2 is still part of A1–A4, so C5 cannot start until A2 is done, while A2 cannot finish until C5 is done.

**Impact:** Neither the current A-before-B/C order nor the tracker dependencies provide a valid next step to close A2 and start C5.

**Suggested correction:** Split A2 completion into the worker/scheduling work and the later C5 integration. Permit C5 to start once its database prerequisites are complete, then close the integration item after C5. Make the A1–A4 gate explicit about this exception. Alternatively, move C5 before the A2 completion gate. Do not leave both dependencies as written.

### F-02 — B1's S4 owner check is required before E1 can run

**Evidence**
- B1's tracker “Done when” requires S4 to be recorded (`fixes/TRACKER.md`, B1).
- S4 is an owner device scenario in E1; device checks are scheduled at the end (`fixes/PLAN.md` §7, S4; §5 Batch E).
- The Batch D gate requires B and C to be done, and the Batch E gate requires D to be done (`fixes/TRACKER.md`, Batch D and Batch E).
- Therefore B1 cannot be done until E1, but E1 cannot start until B1 is done through D.

**Impact:** The plan's own “device checks only at the end” rule conflicts with the gate that requires B1, including its device result, before D.

**Suggested correction:** Separate B1's implementation/automated-test completion from its owner-run S4 result. Let D depend on the former; keep S4 explicitly owner-run pending until E1.

### F-03 — C6 golden-log tests require E1, which requires C6 before it can start

**Evidence**
- C6 requires golden-log tests using owner-recorded logs (`fixes/PLAN.md` §5 C6).
- The tracker blocks those logs on E1/S11 and makes golden-log behavior part of C6's “Done when” (`fixes/TRACKER.md`, C6).
- E1 is gated on D, while D requires B and C done (`fixes/TRACKER.md`, Batch D, Batch E, and E1).
- Consequently C6 needs E1 evidence before it can complete, but E1 waits for D, which waits for C6.

**Impact:** The required device logs cannot be collected at the prescribed end-of-work session and still unblock D.

**Suggested correction:** Move the owner-log-dependent golden-log tests to the E1/close-out gate, or split C6 into pre-E1 work (completeness contract, rollback, seam behavior) and post-E1 golden-log validation. D must not require the E1-dependent portion.

## Conditional gate risk

### F-04 — C2 manifest confirmation may become another D/E1 loop

**Evidence**
- C2 requires owner confirmation of manifest package visibility because the manifest is unavailable (`fixes/PLAN.md` §5 C2).
- The tracker lists that confirmation as owner-run and blocked by “E1 or owner confirmation” (`fixes/TRACKER.md`, C2).
- D requires C to be done, but E1 waits for D.

**Impact:** This is not an unavoidable cycle if the owner confirms before E1. If confirmation is deferred to E1, C2 can hold C, then D, then E1.

**Suggested correction:** Request the manifest/confirmation before D, or record the verified limitation and explicitly allow D to proceed with that owner-run item pending if the plan permits it. Do not make E1 the only route to satisfy C2.

## Acceptance and wording ambiguities

### F-05 — A4's test-coverage gate can be read as requiring future batches early

**Evidence**
- A4 says its work must cover the required tests in section 6 and is done when “the section 6 list is covered” (`fixes/PLAN.md` §5 A4).
- Section 6 includes tests for B, C, and D features that are introduced later (`fixes/PLAN.md` §6.2).
- The tracker instead assigns those tests to their introducing batches and leaves them open until then (`fixes/TRACKER.md`, A4 crosswalk).

**Impact:** A literal reading prevents A4 from finishing before B/C/D; the tracker uses a different, more workable interpretation.

**Suggested correction:** Define A4 as removing source-text tests, adding its own baseline behavior tests, and mapping later section 6 tests to their implementation batches. State that future-batch coverage is assigned, not required to pass in A4.

### F-06 — A2's “Done when” omits a required deliverable

**Evidence**
- A2 requires the maintenance worker to call C5 pruning (`fixes/PLAN.md` §5 A2).
- Its “Done when” mentions only startup scheduling evidence and passing tests (`fixes/PLAN.md` §5 A2).
- The tracker correctly retains a separate unchecked C5 integration item while A2 remains in progress (`fixes/TRACKER.md`, A2).

**Impact:** The plan's completion sentence could permit A2 to be marked done while a required worker responsibility is still missing.

**Suggested correction:** Include the C5 pruning integration in A2's completion criteria, or explicitly label it a cross-batch follow-up that does not block A2 completion.

### F-07 — “Device session once” conflicts with allowed retest rounds

**Evidence**
- The protocol says the owner tests once at the very end (`fixes/PLAN.md` §7, lines 358–369).
- The triage rule then allows up to two rounds of retests for failed scenarios (`fixes/PLAN.md` §7, line 369).

**Impact:** It is unclear whether “once” means one initial full session or literally one owner session with no later device verification.

**Suggested correction:** Say “one initial full device session at the end; then retest only failed scenarios, up to two rounds.”

### F-08 — The owner-approved B1 exception is absent from the plan

**Evidence**
- The plan says not to start a later batch until the earlier batch's “done when” holds, except where the batch permits parallel work (`fixes/PLAN.md` §0).
- The plan orders A before B/C, and the tracker says B cannot start before A1–A4 are done (`fixes/PLAN.md` §5; `fixes/TRACKER.md`, Batch B gate).
- The tracker records the owner's explicit exception to start independent B1 work before that gate, while saying the plan itself is unchanged (`fixes/TRACKER.md`, decision log and B1 notes).

**Impact:** The current implementation status follows the owner's instruction but conflicts with the written plan's global ordering rule.

**Suggested correction:** Record a narrowly scoped B1 exception in the plan, or explicitly classify it as an owner-authorized deviation from the plan. Keep B1's B6-dependent fallback work gated.

### F-09 — Tracker progress summaries are stale

**Evidence**
- The A5 notes say A1–A4 are eligible but “still NOT STARTED” (`fixes/TRACKER.md`, A5 notes), although A1, A3, and A4 are marked complete and A2 is in progress.
- The final summary says B1–B7 are `NOT STARTED` (`fixes/TRACKER.md`, Summary), while B1 is `IN PROGRESS` with a start date and an explicit sequencing exception.

**Impact:** Readers relying on the notes or summary get a different project state from the detailed batch entries.

**Suggested correction:** Refresh the stale A5 note and aggregate B status whenever a batch changes; show B1 separately from B2–B7 so partial progress and its exception remain visible.

### F-10 — Migration-test acceptance changes between A1 and project close-out

**Evidence**
- A1 allows instrumented migration tests to be written and compiled, rather than run, when JVM/Robolectric execution is unavailable, and says to rely on S2 owner testing (`fixes/PLAN.md` §5 A1).
- The final definition of done says “the migration tests pass” as well as requiring S2 on both phones (`fixes/PLAN.md` §10).
- The tracker records the A1 instrumentation tests as compiled but not run (`fixes/TRACKER.md`, A1).

**Impact:** The plan does not say whether compile-only instrumentation plus S2 is acceptable for final completion, or whether runtime execution of every migration test is mandatory.

**Suggested correction:** Make the close-out evidence rule match the A1 fallback (including the exact substitute evidence), or state where and how runtime migration tests must be run.

### F-11 — Post-device tuning has no verification path

**Evidence**
- PD-10 says the three-second session merge gap may be tuned after the device session (`fixes/PLAN.md` §3.1, PD-10).
- E1 is designated the end-of-work device session; the plan does not describe how a resulting C1 code change reopens tests or owner verification (`fixes/PLAN.md` §§5 and 7).

**Impact:** If device results lead to tuning, the change happens after the planned final verification, with no stated re-verification or tracker-reopening rule.

**Suggested correction:** State whether tuning is conditional or required. If it changes code after E1, define which automated tests and owner scenarios must be rerun and which completion gates reopen.

## Dependencies that are not cycles

- **B1 → B6:** B1's fallback behavior needs B6's shared resolver, but B6 does not depend on B1. This is a one-way dependency. The authorized partial-B1 approach records fallback and its tests as deferred until B6.
- **A1/A3 owner checks → E1:** S1/S2 are deferred owner checks, but their tracker “Done when” criteria are automated evidence and explicitly leave those checks pending. They do not block the A batch gate as currently written.

## Recommended repair order

1. Resolve F-01 by breaking the A2/C5 dependency loop.
2. Clarify the shared owner-run gate in F-02 and F-03: implementation readiness may unlock D; device evidence remains pending until E1.
3. Record the authorized B1 sequencing exception in the plan (F-08) and decide whether C2's owner confirmation will be collected before D (F-04).
4. Align the A4/A2 acceptance criteria and migration-test close-out evidence (F-05, F-06, and F-10).
5. Reconcile stale tracker status notes and summaries (F-09).
6. Clarify the initial-session/retest wording and define verification after any post-E1 tuning (F-07 and F-11).

Until the plan and tracker are reconciled, keep B1's agreed independent work separate from its B6-dependent fallback work and do not mark owner-run scenarios complete.
